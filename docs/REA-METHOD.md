# REA-METHOD.md — how the behaviour was reverse engineered

The assignment's central question is *"how do you prove that what the agent
took apart is **correct**?"* This document answers it as a method; the
per-finding answers live in [../SPEC.md](../SPEC.md) and
[EVIDENCE/](EVIDENCE/).

---

## 1. Why black-box, not static analysis

G\*Power is distributed as a closed Windows/macOS binary. Three analysis
routes were available:

| route | what it yields | why it was not chosen as the primary method |
|---|---|---|
| static disassembly | the literal implementation | produces decompiler output, which the submission rules forbid in the deliverable, and which a clean-room reimplementation may not read anyway (it would make the second session derivative) |
| source recovery | nothing — it is not published | — |
| **behavioural (black-box) probing** | the input→output map, which is what a reimplementation must reproduce | chosen |

The decisive argument is not legal convenience, it is **relevance**. A
conformance gate is stated over outputs: *given these inputs, does your N match
theirs?* The object that answers that question is the input→output map, and
black-box probing measures it directly. Static analysis would measure a
different object (the code) and then require an inference step back to
behaviour — more work, more assumptions, and a deliverable that cannot be
shipped.

So the method is **differential testing against the reference
implementation**, with the reference treated as an oracle that can be queried
but not read.

---

## 2. The probe design rule: never observe, always discriminate

A probe that merely records "G\*Power said 210" proves nothing: any number of
different implementations say 210. Every probe in [EVIDENCE/](EVIDENCE/)
therefore follows the same four-step shape.

1. **Enumerate candidate behaviours.** Not one hypothesis — at least two,
   each of which a competent implementer might plausibly have written. For
   the two-tailed power formula (E-002) the candidates are "far tail kept" and
   "far tail dropped"; for the allocation grid (E-009) they are "search per
   group" and "search the total".
2. **Find an input where the candidates disagree by more than the printed
   precision.** This is the creative step and it is where the work is. For
   E-002 the trick is to push the effect size to zero, where the two formulas
   differ by a factor of two instead of by `1e-9`. For E-005 it is to search
   for a design where an odd split already clears the target power.
3. **Write down the predicted output of each candidate before observing.**
   Pre-registration, in miniature. The predictions are generated *by running
   the engine*, so they cannot be retrofitted after the fact —
   `tools/probe_plan.py` recomputes them on every run, and a prediction that
   drifted from the implementation would show up as a changed worksheet.
4. **Add a control row** on which the candidates agree. If the control fails,
   the probe was mis-operated and the discriminating rows are void. Eight of
   the 36 worksheet rows are controls.

The output of step 3 is a falsifiable claim. That is the thing the assignment
asks for, and it is why the evidence files are structured around
*competing predictions* rather than around observations.

## 3. What counts as `[GÖZLEM]` evidence here

Every finding in SPEC.md carries the label **`[GÖZLEM]`** and one status. The
statuses say *how* the claim is established; the label says it is claimed as
reverse-engineered behaviour, with evidence, and not copied from the manual.

| status | how it is established | findings |
|---|---|---|
| `[GÖZLEM]` | a recorded G\*Power 3.1.9.6 reading settles it, with a competing prediction it refutes | F-02, F-05, F-06, F-12, F-14 |
| `[TÜRETİLMİŞ + GÖZLEM]` | forced by internal consistency between menu entries, **and** confirmed by a reading | F-01, F-03, F-04, F-07, F-10 |
| `[GÖZLEM: ÇÜRÜTÜLDÜ → DÜZELTİLDİ]` | the pre-registered prediction was **wrong**; the finding now states the observed rule | F-08, F-09 (and one clause of F-06) |

### Derivation — proof by internal consistency

The family contains three places where two different menu entries describe the
**same statistical hypothesis** under different parameterisations:

```
point biserial (r)          ≡  two independent means (d) on a balanced dichotomy
regression coefficient (f²) ≡  point biserial (r), with p = 1
matched pairs (dz)          ≡  one sample (d)
```

A tool that is internally consistent *must* return identical numbers for these
pairs. That pins the noncentrality convention: of the candidate forms for the
point-biserial noncentrality, only `r·√(N/(1-r²))` reproduces the two-group
result (E-004). Each derivation is an executable test
(`tests/test_engine_invariants.py`) — and each has since been confirmed on the
real program as well.

### Observation — and what pre-registration bought

The predictions in `probes/probe_worksheet.csv` were generated by the engine
and **committed before G\*Power was run once**. The observations were then
written into the `observed` column only; `tools/stamp_worksheet.py` refuses to
touch anything else and `tools/probe_plan.py` refuses to regenerate a worksheet
that holds observations. The result is a record of what the engine predicted
and what the program did:

```
SUPPORTS 26   AMBIGUOUS 5 (control rows)   CONTRADICTS 2   PENDING 3 (F-11 drawer)
```

The two `CONTRADICTS` rows are the most valuable output of the whole project.
They are exactly where the specification was guessing — F-08 and F-09 had been
marked open — and on F-09 the observations then showed that **neither** of the
two candidates was right. No amount of testing the engine against itself, or
against SciPy and statsmodels, could have found that: all three agreed with
each other and all three were wrong about G\*Power.

## 4. The probe apparatus

### 4.1 Driving the real GUI, black box

`tools/gpower_ax.py` operates G\*Power for macOS through the **macOS
Accessibility API** — the interface screen readers use. It does exactly what a
person with a mouse does, and nothing more:

1. selects *Test family*, *Statistical test* and *Type of power analysis* from
   the pop-up menus;
2. finds each input field by the label printed next to it and types the value
   (in the GUI's own decimal format — the probing machine used a comma locale);
3. presses **Calculate**;
4. reads back both panels: the *Input parameters* (so a swallowed keystroke is
   detected — the campaign re-tries, then discards the reading) and the
   *Output parameters*;
5. captures any dialog G\*Power raises (*"Input error!"*, *"Internal Math
   Error!"*) and dismisses it.

It never reads process memory, never loads or disassembles the binary, never
touches a file inside the application bundle. The application was the
notarised `GPowerMac_3.1.9.6.zip` from the authors' site, signed by its author;
it lives outside the repository and is not distributed with it.

### 4.2 Campaigns

`tools/rea_campaign.py` runs named case sets through the GUI **and** through
the engine and appends one JSON record per case to
`probes/observations/gpower-3.1.9.6-macos*.jsonl`:

| set | rows | purpose |
|---|---|---|
| `probes` | 35 | the pre-registered worksheet rows |
| `alloc` | 48 | allocation-ratio sweep (F-09) |
| `sweep` | 41 | fine power sweep at one unbalanced design — exposed F-09's stopping test |
| `sign` | 12 | negative effect sizes across tests and analyses (F-08) |
| `domain` | 22 | edges of the input domain (F-15) |
| `grid` | 240 | seeded random conformance grid over all 6 tests × 5 analyses |

The raw records are never edited. `tools/rea_report.py` re-runs the *current*
engine on every recorded input and compares every printed field at G\*Power's
printed precision ([`probes/REA-OBSERVED.md`](../probes/REA-OBSERVED.md));
`tests/test_gpower_observed.py` does the same in CI, without G\*Power.

### 4.3 From observations to a rule

Where the observations refuted the candidates, the next probe was designed to
expose the mechanism rather than to collect more instances. For F-09 that was a
power sweep at fixed design: a staircase of `N` against target power separates
"which grid is searched" from "which split the stopping test sees", and it did
(E-009). `tools/fit_allocation.py` then scores every candidate rule against
every recorded row, so the choice is a table, not an argument.

### 4.4 The worksheet loop

```console
$ python tools/stamp_worksheet.py       # observed column, from probes/observations/
$ python tools/harvest.py               # verdict per row and per finding
```

| verdict | meaning |
|---|---|
| `SUPPORTS` | matches the engine **and** differs from the competing candidate |
| `AMBIGUOUS` | matches both (control rows, by construction) |
| `CONTRADICTS` | matches the competing candidate — the engine is wrong |
| `UNEXPLAINED` | matches neither — a third behaviour exists, widen the candidate set |
| `PENDING` | not yet observed |

## 5. Proving correctness *without* the oracle

The oracle is not always available — not on CI, not on a grader's machine, not
for a reader of this repository. Five independent checks therefore run with no
G\*Power present at all.

### 5.1 An independent re-implementation of the same spec

`tests/test_reference_scipy.py` rebuilds the whole family from the formulas in
SPEC.md using `scipy.stats.nct` and `scipy.stats.t`, and searches the sample
size by **brute-force linear scan** rather than the engine's bracketing
search. All 401 bundled vectors are re-derived. Two implementations, two
noncentral-*t* evaluations, two search strategies, one answer:

```
401/401 exact N agreement · worst post-hoc power deviation 1e-10
```

This catches exactly the class of bug the engine is most exposed to: a
numerical slip in the hand-written quadrature, or an off-by-one in the
bracketing search.

### 5.2 An implementation written by other people

`tests/test_reference_statsmodels.py` compares against
`statsmodels.stats.power` — not a reference we wrote, but an independent
implementation of the same procedures from the statistical literature.

That distinction carries real weight: §5.1 shares our *reading* of `SPEC.md`,
so it can catch a miscomputation but never a misreading. statsmodels can. And
on the finding where a misreading was most plausible — whether the two-tailed
expression keeps the far-tail term (E-002) — it independently keeps it, at
every `α` tested. Candidate A is thus the expression two unrelated
implementations arrived at, which is a different kind of evidence from an
argument about test size.

It is used strictly as an **agreement** oracle, never an accuracy one — and
the reason is version drift, not quality. On the development machine
(statsmodels 0.15.0, SciPy 1.14.1) its error reached `7.2e-5` as power
approached 1, returning exactly `1.0` where the truth is `0.99997773…`,
against `1.2e-11` for this engine. On the versions CI installs it is accurate
to `3.3e-16` and the comparison inverts. Bounding the engine with *either*
would have tied this project's error bar to a dependency's release schedule.
The two roles are kept apart in [VALIDATION.md §2b](VALIDATION.md), and the
test handles both cases explicitly so it cannot quietly change meaning.

### 5.3 Property tests instead of golden values

`tests/test_engine_invariants.py` encodes properties that any correct
implementation must satisfy, so they stay meaningful even if every golden
number were wrong:

* power is monotone in `N`, in `α` and in `|ES|`, for all five tests;
* the a-priori answer is both **sufficient** (`power ≥ target`) and **minimal**
  (one step down misses the target) — checked per test, per target, per tail
  count;
* the five analysis types round-trip: a priori → post hoc reproduces the
  power; criterion → post hoc reproduces the target; sensitivity → post hoc
  reproduces the target; compromise satisfies `β/α = q` and `power = 1-β`;
* the three cross-entry identities of §3 hold exactly.

### 5.4 Arbitration by a fourth oracle — and a lesson learned twice

Neither SciPy nor statsmodels is ground truth. At `df = 75, p = 0.95` the
central-*t* quantile, on the development machine, was:

```
exact (mpmath, 50 digits)  1.6654253733225633
this engine                1.6654253733225670   (3.8e-15 off)
SciPy 1.14.1               1.6654253734015287   (7.9e-11 off)
```

The critical value feeds every power number in the project, so "trust SciPy"
would have capped the engine's error bar four orders of magnitude above what
it achieves. Whenever the engine and an external library disagree beyond
`1e-13`, a 50-digit `mpmath` computation arbitrates, and the result is
recorded in [VALIDATION.md](VALIDATION.md). Six numerical defects in the
engine were found and fixed this way (all documented in
[SPEC §4](../SPEC.md#4-numerical-requirements)).

**Then the lesson arrived a second time, pointing the other way.** An early
draft of the tests asserted that the engine *beat* SciPy and statsmodels at
these points. CI installs newer versions of both, and on those the same
quantile is accurate to `4.4e-16` — better than this engine — and the
statsmodels saturation is gone. The assertion failed, correctly.

So the rule is sharper than "the libraries are worse":

> **A library's numerical accuracy is a property of its version.** Whichever
> way the comparison runs today, an external library must not be the thing
> that bounds your own error bar.

The tests now assert the engine's own error against an exact oracle, and mere
*agreement* with the libraries at a tolerance wide enough for any version;
which one is closer is not asserted at all. The overclaim is recorded in
[VALIDATION §3.2](VALIDATION.md) rather than quietly deleted, because it was
caught only by running CI on a different dependency set than the laptop — which
is the whole argument for doing that.

And the companion rule, from §7: **a second implementation settles what the
answer is; only a higher-precision computation settles who is right.**
Conflating the two is how a project inherits a dependency's error bar.

### 5.5 Self-consistency of the quadrature

The noncentral-*t* CDF is evaluated as `E_S[Φ(t·S − δ)]`. The weight `S`
integrates to 1 by construction, so integrating the quadrature weights alone
measures the quadrature's own error with no oracle whatsoever:

```
df = 1 … 100 000   →   |mass − 1| ≤ 2.1e-14
```

## 6. What the method cannot establish

Stated plainly, because the credibility of everything else depends on it.

* **Black-box probing cannot prove the absence of special cases.** A region of
  the input space that was never probed may behave differently. The mitigation
  is coverage — all six tests, all five analyses, a seeded random grid, ratio
  and power sweeps, domain edges — not a proof, but a bounded claim.
* **One platform, one version.** Every reading is from G\*Power 3.1.9.6 for
  macOS. The current Windows build is 3.1.9.7; nothing here shows it behaves
  identically, and that has not been checked.
* **F-11 is still open.** The effect-size drawer is a separate dialog the
  driver does not operate yet; its three probe rows are `PENDING`.
* **The engine is not G\*Power.** It reproduces a specification of one test
  family. `engine_provenance` (the MCP tool an agent calls when a user asks
  "can I trust this?") says so, and so does [ETHICS.md](../ETHICS.md).

## 7. Reproducing the whole chain

```console
$ pip install -e ".[mcp,agent,dev]"

$ python tools/compliance_check.py     # submission rules as a machine check
$ python tools/make_vectors.py --check # vector file is not stale
$ python -m pytest -q                  # incl. the SciPy re-derivation and every G*Power reading
$ gpower selftest                      # 401/401 exact N

$ python tools/rea_report.py           # engine vs every recorded G*Power reading
$ python tools/fit_allocation.py       # F-09: candidate rules vs the readings

# with G*Power for macOS running and Accessibility permission granted:
$ python tools/rea_campaign.py --set all
$ python tools/stamp_worksheet.py && python tools/harvest.py
```

Everything above the comment runs offline, with no third-party runtime
dependency for the engine itself.
